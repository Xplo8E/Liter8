# iPhone 11 `24A446`: tfp0 kernel read/write

- Device: iPhone 11 (`iPhone12,1`, `n104ap`)
- OS: iOS 27.0.1 (`24A446`)
- Kernel: XNU `13432.2.10~2`, arm64e, booted as `PATCHED_ARM64_T8030`
- Result: PID 0 task port, live kernel base and kernel read confirmed, with
  `TASK_DYLD_INFO` left intact for every other task

`fw get-boot --tfp0` adds the tfp0 patches used by `libkrw0-tfp0`. Each site is
found by a unique relocation-tolerant instruction sequence; nothing is a fixed
offset. The approach follows the PongoOS KPF reference, except for the slide
transport, which is scoped here (see below).

| Patch | Offset | Original | Replacement |
| --- | ---: | --- | --- |
| task conversion | `0x31b6640` | `1f0009eb` | `ff031feb` |
| PID zero | `0x36bf37c` | `f7070034` | `1f2003d5` |
| kernel map | `0x31b7fa8` | `41010054` | `0a000014` |
| slide shim cave | `0x39fd53c` | 56 zero bytes | `6893fed0…a60be017` |
| `TASK_DYLD_INFO` site | `0x32003f8` | `88f241f9` | `51f41f14` (B to the cave) |

## Why the slide is scoped to the kernel task

The straightforward version of the last patch rewrites the shared
`TASK_DYLD_INFO` result path so it returns `0` and `vm_kernel_slide`. That path
never tests which task was asked about, so **every** task loses its real dyld
info. Measured on this device with the unscoped form:

- every task reported `all_image_info_addr=0x0`, with the kernel slide in the
  size field, so any unentitled process could read the slide
- `_dyld_process_info_create` failed `kr=5` for every pid
- lldb attached but reported `(No executable module.)`, an unsymbolized
  backtrace, and `image list` → `error: the target has no associated
  executable images`
- Settings was watchdog-killed at `scene-create` after ~19.9 s and never
  opened. It blocks in `MKBGetDeviceLockState` → `get_aks_client_connection`,
  behind a thread wedged uninterruptibly in the kernel on `aks-client-queue`,
  so every MobileKeyBag caller hangs

A per-record bisect over eight boots showed no single tfp0 patch regresses
MobileKeyBag, and that `task-conversion + pid-zero + kernel-map` yields a fully
working tfp0 with a healthy MobileKeyBag. The slide patch is therefore not
load-bearing for tfp0 itself, only for how libkrw learns the slide. Why the
unscoped slide patch combined with a working tfp0 wedges AppleKeyStore is **not
established**; each is harmless alone.

The site now branches into a cave that compares the task in `X20` against
`kernel_task`, returns the slide for that one task, and replays the four
displaced instructions unchanged for everyone else. Both globals are recovered
semantically: `vm_kernel_slide` from the kernel-slide log string, `kernel_task`
from the ADRP/LDR pair the task-conversion site already uses.

## Runtime result, scoped build

Read back from live kernel memory through tfp0, slide `0x3c304000`:

```text
site 0xfffffff00a2043f8 -> 51f41f14                     (B to the cave)
cave 0xfffffff00aa0153c -> 6893fed0083145f99f0208eb…    (all 56 bytes match the record)
```

The slide is correct, not merely plausible: reads at `unslid + 0x3c304000`
returned `ff031feb` at the task-conversion site and `1f2003d5` at the PID-zero
site.

```text
self       all_image_info_addr=0x204d7e670 all_image_info_size=0x170
launchd    all_image_info_addr=0x104e00070 all_image_info_size=0x170
kernel     all_image_info_addr=0x0         all_image_info_size=0x3c304000
task_for_pid(0) kr=0 port=0x1b03
MKBGetDeviceLockState -> 0, three of three runs
_dyld_process_info_create(pid 1) -> 93 images
lldb image list -> 78 images, symbolized backtrace through sleeper`main
```

Settings, Sileo and Safari were each opened several times with no failure. On
the same device the unscoped build produced ten Preferences watchdog kills
across two boots and zero on a `boot-jit` boot.

The 24B119 repeat boot reproduced every line above: real dyld info for normal
tasks, slide only for the kernel task, `MKBGetDeviceLockState` returning three
of three, 94 images through `_dyld_process_info_create`, and kernel read and
write both clean.

## Scope

Runtime was tested on `24A446` and `24B119` (see below). `24A435`, `24A437`,
`24B5084k`, `24B5089g`, `24B5099f` and `24B5110a` are resolver verified against
their own kernelcaches, with exact-output fixtures for `24A435` and `24A446`.
The 27.2 RC `24B115` is deliberately absent: it embeds the same XNU string as
`24B119`, which would make `KernelResolverProfileRegistry.detect` ambiguous and
silently disable every kernel resolver for both builds.

Not established here: writes to SPTM-protected memory, and whether
`libkrw0-tfp0` reads the slide from the kernel task or from `mach_task_self()`.
If it uses the latter it needs a one-line change to pass the kernel task port.
The plugin was not installed on this device, so every measurement above used a
local probe querying the kernel task.

## Second runtime result: iOS 27.2 `24B119`

Same patches on the 27.2 release build, kernel `xnu-13432.42.3~28`. Normal boot
from an existing `.ios272r` work directory, no restore, then a repeat boot of
the same signed artifact set. First boot's slide was `0x3a34c000`, the repeat's
`0x4710c000`, and both resolved every patched site correctly, so the shim reads
the live global rather than a value fixed at build time. Figures below are the
first boot.

Kernel read and write, against a scratch allocation in the kernel map:

```text
kalloc   kr=0 address=0xffffffed3b4a0000
kwrite   kr=0
kread    kr=0 out=24 data="libkrw-read-write-check"
kdealloc kr=0
```

Reads of live kernel text are covered by the table below. Writes were exercised
only against that scratch allocation, not against live kernel structures or
SPTM-protected memory. Note the kernel-map patch removes the panic that would
otherwise catch a bad write, so a buggy client corrupts silently instead.

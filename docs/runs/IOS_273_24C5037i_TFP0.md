# iPhone 11 `24C5037i`: tfp0 kernel read/write

- Device: iPhone 11 (`iPhone12,1`, `n104ap`)
- OS: iOS 27.3 beta 1 (`24C5037i`)
- Kernel: XNU `13432.60.57~17`, arm64e, booted as `PATCHED_ARM64_T8030`
- Result: PID 0 task port, live kernel slide via the scoped cave, kernel-map
  write/read round trip, and a patched byte confirmed live in `__DATA_CONST`.
  One new 27.3-specific finding: reading execute-only kernel text through the
  port freezes the machine. Data-region readback is safe.

`fw get-boot --tfp0` adds the tfp0 patches used by `libkrw0-tfp0`; every site
is found semantically on this kernelcache, nothing is a fixed offset. The boot
was built with `--serial` on the same artifact set used for the reviewed
device run, so boots two through five of 2026-11-10 are all that artifact set,
with tfp0 present from the first.

| Patch | File offset | Original | Replacement |
| --- | ---: | --- | --- |
| task conversion | `0x33376e4` | `1f0009eb` | `ff031feb` |
| PID zero | `0x384ce40` | `f7070034` | `1f2003d5` |
| kernel map | `0x333904c` | `41010054` | `0a000014` |
| slide shim cave | `0x3b9153c` | 60 zero bytes | trampoline |
| `TASK_DYLD_INFO` site | `0x3381708` | `88f241f9` | `8d3f2014` (B to the cave) |

Unslid addresses, from the kernelcache segments (`__PRELINK_TEXT` vmaddr
`0xfffffff00700c000`, fileoff `0x8000`): task conversion `0xfffffff00a33b6e4`,
PID zero `0xfffffff00a850e40`, kernel map `0xfffffff00a33d04c`,
`TASK_DYLD_INFO` site `0xfffffff00a385708`. The cave grew from 27.2's 56 bytes
to 60 and sits at the end of `__TEXT_EXEC`.

## Runtime results, two boots of one artifact set

First evidence boot: slide `0x45418000`. Second: slide `0x44174000`. Two
different slides reading every measurement correctly shows the shim reads the
live global rather than a build-time value, the same cross-boot check the
24B119 run used.

```text
task_for_pid(0) kr=0 port=0x1d03       (repeatable, port differs per call)
task_info (BASIC_INFO) kr=0 suspend_count=0
self       all_image_info_addr=0x1fbf5a600 all_image_info_size=0x170
launchd    all_image_info_addr=0x102478000 all_image_info_size=0x170
kernel     all_image_info_addr=0x0         all_image_info_size=0x44174000

kalloc   kr=0 address=0xffffffebbaa64000
kwrite   kr=0
kread    kr=0 out=29 data="libkrw-read-write-check-27.3" match=1
kdealloc kr=0
```

Live readback of a patched byte. The exception-port behavior byte is part of
`boot-jit`, not tfp0, but it sits in `__DATA_CONST`, which is exactly where a
readback that does not touch execute-only text can still prove both the slide
and that a patch is live in memory. On-disk pre-patch bytes are `01000000`;
the boot replaces the first byte with `00`:

```text
read 0xfffffff04bd87278   (0xfffffff007c13278 + slide 0x44174000)
     kr=0 00000000        matches the patched record exactly
```

## 27.3 finding: execute-only text readback freezes the kernel

The 24A446 and 24B119 runs verified all patched sites by reading the live
bytes of `__PRELINK_TEXT` through the kernel task port. On 27.3 the same
operation stops the machine: the first evidence probe ran every phase at once
and dropped SSH and Wi-Fi together with no panic report persisted
(`/var/mobile/Library/Logs/CrashReporter` gained a boot-time watchdog
stackshot from that boot, not a panic-full). A phase-isolated rerun on a
fresh boot bisected it exactly:

| Phase | Result |
| --- | --- |
| `task_for_pid(0)` + `task_info(BASIC_INFO)` | clean |
| `TASK_DYLD_INFO` self + launchd | clean |
| `TASK_DYLD_INFO` kernel task (cave branch) | clean, slide delivered |
| kernel-map kalloc/write/read/dealloc | clean |
| `mach_vm_read_overwrite` on `__PRELINK_TEXT` | freezes the kernel, reproducibly |

Two freezes, both in the read phase, both with no panic store entry: this is a
hang, not a crash, so 27.3's kernel does not fault cleanly on cross-copyio
access to execute-only pages the way 27.2's did. Consequence for tooling:
verify live patches in `__DATA_CONST`/`__DATA`, not in text. The tfp0
capability itself is unaffected - the freeze needs a client that reads text,
and libkrw clients read and write data.

Not established here: writes to SPTM-protected memory, and whether the freeze
is text-page-specific or applies to `__TEXT_EXEC` and `__TEXT_BOOT_EXEC`
equally - establishing that costs one frozen phone per data point and the
`__DATA_CONST` readback already covers what the evidence needs.
